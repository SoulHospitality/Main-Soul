# Financial Integration Matrix

**Status:** Phase 5, 2026-11-24, offline analysis. Nothing in this matrix posts to the stored ledger: posting is off and blocked by the database until D-01, the VAT base and the commission methodology are approved.

**How to read it:**
- **Today**, the books are **computed** by `lib/finance/ledgerEngine.js` (`buildJournal`) from operational tables every time they are viewed. Each source record produces entries with a stable id (for example `BK-{reservation}`).
- **Proposed** is how the same event will post to the stored ledger through `lib/accounting/posting.js`.
- **Idempotency key:** each proposed key carries a version (`…:v{n}`). An edited source record gets a new version that is posted as **reversal + replacement** (`replaceEntry`). It is never posted as a second, silently different entry with the same key; the database refuses that with `IDEMPOTENCY_CONFLICT`.
- **Treatments marked ⚠ depend on unresolved decisions** (D-01 presentation, D-11 VAT base, D-05 FX). The matrix records today's treatment only. It does not decide them.

## Findings from the trace
- **No application path writes to the stored ledger, the posting switch, policies or snapshots.** A code search found no route touching `ledger_*`, `commission_snapshot*` or `ledger_posting`. The only settings write (`PUT /financial-system/settings/:key`) whitelists `gateway_mdr_pct`; security-test confirms an admin cannot flip posting through it.
- **Edits recompute history in open months** (rows 1, 12, 14, 24): this is audit finding L2. The stored ledger cannot do this. It needs versioned keys and replacement (implemented: `replaceEntry`, `IDEMPOTENCY_CONFLICT`).
- **Gaps:**
  - G-3: chargebacks are not modelled.
  - G-4: no distinct no-show treatment.
  - G-5: no payroll posting.
  - T-2: insurance, vendor invoices, recurring charges, petty cash, housekeeping orders and holdbacks are not yet in the synthetic fixtures.
  - T-3: the Paymob webhook (HMAC, amount check, duplicate callback) has no automated test.
